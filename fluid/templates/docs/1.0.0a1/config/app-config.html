Configuration

App Configs

In the previous chapter we built our first and simple app. And we had to create an app.ini file to run it. So we can say that app configs play a central role in spinning up your apps and developing WebFluid projects.

The core concept

App configs are built to replace .env files and provide an easy way to spin up multiple apps inside one project. You create an app_configs/[app].ini file and then the CLI uses its name to perform app-specific commands like running it or migrating its database.

Primarily it is used to store secrets, potentially risky information (like database uris) and switches. Switches are another core concept of WebFluid. The framework uses them to enroll features and extensions on startup. Or in other words: They make the framework magic optioned.

Sections

App configs are parsed using Pythons configparser. Primarily, we are using sections to logically separate parts of your apps' configuration. The most important sections are:

DEFAULT / general

The [DEFAULT] or [general] section is used to store some of the basic information like your apps SECRET_KEY and whatever you think is part of it too.

{{ info(''' We used "general" for our logical defaults, but since it is just logical separation, you are not forced to stick with our defaults. This, of course, applies to all the sections explained in this article. ''') }}

extensions

Extension switches are written into the [extensions] section. All of our extension switches are prefixed with EXT_. They are used to enable the frameworks' default extensions.

features

Framework feature flags are separated into the [features] section. They are switches that toggle framework functionality like request logging, exception handling and default endpoints. Feature flags are prefixed with WF_.

data / mail

We use sections like [data] and [mail] to store extension-specific configuration values there. This can be database uris, mail server authentication details and other potentially insecure information.
